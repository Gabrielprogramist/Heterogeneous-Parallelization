# CUDA Overlap Project — Sync vs Async (Streams + Chunks)

## Что это за проект

Этот репозиторий показывает на практике, как в CUDA можно уменьшить **общее end-to-end время** (копирование данных на GPU → вычисление → копирование обратно), используя **перекрытие (overlap)** передачи данных и вычислений.

В репозитории лежат **две самостоятельные реализации одной идеи** (sync vs async) под разные сценарии запуска:

* **`overlap.cu`** — вариант, удобный для **Google Colab** (и вообще для “учебного” эксперимента).
  Поддерживает переключение **pinned/pageable host memory**, параметр **`--iters` как вычислительную нагрузку ядра**, медиану по прогонам и подробный вывод.
* **`final_project.cu`** — вариант для **локального запуска** (ноутбук/ПК/сервер с CUDA Toolkit).
  Также сравнивает sync и async с **streams + chunks**, ориентирован на быстрый локальный запуск и замеры.

Обе программы демонстрируют один и тот же принцип:

* **Sync**: последовательно `H2D memcpy → kernel → D2H memcpy`
* **Async**: разбиение на чанки + `cudaMemcpyAsync` + несколько streams, чтобы копии и kernel могли идти параллельно.

---

## Ключевая идея эксперимента

В синхронной версии общее время близко к сумме:
`T_sync ≈ T(H2D) + T(kernel) + T(D2H)`

В асинхронной версии при правильных настройках:

* копирование следующего чанка может выполняться, пока GPU считает текущий,
* выгрузка предыдущего чанка может перекрываться с вычислением и/или загрузкой,
* итоговое время стремится к “узкому месту” конвейера (примерно `max(copy_pipeline, compute_pipeline)`), поэтому **end-to-end уменьшается**.

## Запуск в Google Colab (для `overlap.cu`)

### 1) Включить GPU

`Runtime → Change runtime type → Hardware accelerator: GPU`

Проверка:

```bash
!nvidia-smi
```

### 2) Установить nvcc в Colab через nvcc4jupyter

```bash
!pip -q install nvcc4jupyter
%load_ext nvcc4jupyter
```

### 3) Компиляция (пример для Tesla T4 / sm_75)

```bash
!nvcc -O3 -std=c++17 overlap.cu -o overlap \
  -gencode arch=compute_75,code=sm_75
```

### 4) Запуск

Пример (512 MiB, чанки 32 MiB, 4 стрима, pinned):

```bash
!./overlap --bytes 536870912 --chunk 33554432 --streams 4 --iters 256 --pinned 1 --warmup 1 --reps 5 --verify 1
```

### Параметры `overlap.cu`

* `--bytes` — общий размер данных (байты)
* `--chunk` — размер чанка (байты)
* `--streams` — число CUDA streams
* `--iters` — вычислительная нагрузка ядра (чем больше, тем дольше kernel)
* `--pinned` — `1` pinned host memory (обычно сильнее overlap), `0` обычная память
* `--warmup` — прогревочные прогоны
* `--reps` — число измеряемых прогонов (в отчёте используется медиана)
* `--verify` — проверка корректности результата

## Как читать результаты

Обе программы выводят (в близком смысле):

* параметры эксперимента (объём данных, chunk, streams, др.)
* **время Sync** (end-to-end)
* **время Async** (end-to-end)
* **ускорение** (`speedup = T_sync / T_async`, больше 1 — лучше)

В `overlap.cu` дополнительно печатается разбиение sync времени на:

* `H2D`, `Kernel`, `D2H` (как ориентир, что именно доминирует).

## Рекомендованные эксперименты (для отчёта/выводов)

### 1) Показать влияние pinned памяти (актуально для `overlap.cu`)

Сравнить:

* `--pinned 1`
* `--pinned 0`

На больших данных pinned обычно:

* ускоряет копии,
* делает асинхронность “реальной”,
* усиливает overlap.

### 2) Подобрать размер чанка

Запустить несколько вариантов (например 8/16/32/64 MiB) при фиксированных `streams`:

* маленький chunk → больше накладных расходов (много запусков memcpy/kernel)
* слишком большой chunk → конвейер “грубее”, overlap может ухудшиться
* обычно есть “середина”, где время async минимально

### 3) Изменить число streams

* `streams = 1` обычно почти не даёт overlap
* `streams = 2..4` чаще всего уже показывает основной выигрыш
* дальше эффект часто насыщается (ограничение по copy engines/пропускной способности)

### 4) Изменить соотношение compute/copy (актуально для `overlap.cu`)

Меняя `--iters`, можно увидеть:

* при малом `iters` эксперимент более copy-bound (overlap особенно заметен)
* при большом `iters` experiment compute-bound (ускорение от overlap уменьшается)

## Типичные причины “почему overlap не видно”

* слишком маленький объём данных (копии и kernel слишком короткие)
* `streams = 1`
* pageable host memory вместо pinned (особенно заметно в Colab)
* слишком маленький chunk (overhead доминирует)
* GPU/платформа ограничены пропускной способностью или особенностями виртуализации
